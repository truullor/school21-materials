# DSB6 — Теория тестирования с PyTest

Как думать о тестах, чтобы их писать: что проверять, почему, в каком порядке. Без готового кода — сначала смысл.

## Зачем нужны тесты вообще
Код пишется один раз, а запускается сотни раз — руками, в отчёте, при ревью. Тесты — это страховка: ты один раз записал «метод должен вести себя так», и потом машина сама проверяет это после каждой правки.

Польза конкретно в проекте:
1. поймать, если метод вернул не тот **тип** (наш dict уехал в list);
2. поймать, если **сортировка** сломалась (метод обязан возвращать отсортированные данные);
3. поймать, если считаются **не те числа** (метрики вручную посчитаны и сверены).

## Как pytest сам себя организует (без твоего участия)
PyTest ищет тесты автоматически по **соглашениям об именах**:

| что | как должно называться |
|---|---|
| файл | `test_*.py` или `*_test.py` |
| класс теста | начинается с `Test` |
| тест-метод | начинается с `test_` |

В нашем модуле `movielens_analysis.py` создан класс `Tests` (подходит под `Test*`) с методами `test_...`. `pytest` подхватывает их прямо из класса внутри модуля.

## Главное правило теста: ОДИН `assert`
Любой тест — это просто проверка-утверждение:

```python
assert <выражение>
```

- истина → тест зелёный (passed);
- ложь → тест красный (failed), pytest покажет какое именно выражение не выполнилось.

Три-четыре assert'а в одном тесте — нормально, если они про один метод.

## Три вещи, которые говорит README проверять
Читаем задание буквально, по пунктам:

### 1. «метод возвращает данные корректных типов»
Наши методы возвращают `dict`. Значит, на входе любого теста:

```python
res = classes.method()
assert isinstance(res, dict)
```

### 2. «элементы списков имеют корректные типы»
У `dish` два уровня типов — **ключи** и **значения**. Проверяем обе стороны:

```python
assert all(isinstance(k, int) for k in res)       # все ключи — int
assert all(isinstance(v, int) for v in res.values())   # все значения — int
```

Что должно быть ключом/значением — смотрим на метод:
- `dist_by_release`: ключи = годы (int), значения = счётчики (int);
- `dist_by_genres`: ключи = жанры (str), значения = счётчики (int);
- `top_by_ratings`: ключи = названия (str), значения = оценки (float, округлённые до 2).

### 3. «данные отсортированы корректно»
Способ проверить сортировку — сравнить последовательность с её отсортированной копией:

```python
# по убыванию
assert list(res.values()) == sorted(res.values(), reverse=True)

# по возрастанию
assert list(res.keys()) == sorted(res.keys())
```

Если порядок не совпал — тест упадёт, и это ровно то, что задание требует отловить.

## Разбор конструкции `all(x for x in values)`
```python
all(isinstance(k, int) for k in res)
```
- `isinstance(k, int)` — лево направо: «k — целое число?»
- `for k in res` — «для каждого ключа по очереди»
- `all(...)` — «TRUE только если каждый вернул истину»

Результат: «все ключи — целые». Если хоть один не int — False → тест красный.

Ту же форму используем на списке значений через `.values()`.

## Ещё важные проверки (бонус к README)

### Округление до 2 знаков
В метриках (`top_by_ratings`, `top_controversial`) значения должны быть `round(..., 2)`. Проверка:

```python
assert all(round(v, 2) == v for v in res.values())
```
Если значение `3.1415`, то `round(3.1415, 2)` = `3.14` ≠ `3.1415` → тест упадёт. Заметит, если округление забыли.

### Размер топ-n
Топы возвращают не больше n записей:

```python
assert len(res) <= n
```
(`<=`, а не `==`, потому что фильмов с оценками может быть меньше n — тогда их меньше, но не больше.)

### Базовые числа (проверка вычислений)
Утилиты (`average`, `median`, `variance`) проверяем на вручную посчитанных значениях — это защита от ошибки в формуле:

```python
assert average([1, 2, 3]) == 2.0     # (1+2+3)/3
assert median([1, 2, 3, 4]) == 2.5  # между 2 и 3
```
Так README говорит: «вручную посчитай результаты и убедись, что методы возвращают верные значения».

## Использование аргумента `metric`
`top_by_ratings(n, metric=average)` принимает функцию. В тесте проверяем и медиану:

```python
res = rm.top_by_ratings(10, metric=median)
```
Так проверяется, что метод работает и со стандартной метрикой, и с переданной.

## Как запускать тесты
Из папки проекта с виртуальным окружением:

```
cd .../src/DSB6
./bin/python -m pytest ../movielens_analysis.py -v
```

`-v` (verbose) — печатает каждый тест отдельно + `passed/failed`. Полезно при первом запуске, дальше хватит без `-v`.

## Что значит «зелёный» / «красный»
- `PASSED` — метод отработал и все assert'ы прошли;
- `failed` — где-то assert ложный; pytest покажет строку и выражение;
- `ERRORS` / `ERROR` — тест упал ещё до assert (например, файл не найден).

Запустил → зелёное → задача по этой части закрыта. Как говорит README: «Перед переходом к следующему этапу запусти тесты».

## Мини-шпаргалка проверок

| хочу проверить | выражение |
|---|---|
| возвращает словарь | `assert isinstance(res, dict)` |
| все ключи — числа | `assert all(isinstance(k, int) for k in res)` |
| все ключи — строки | `assert all(isinstance(k, str) for k in res)` |
| все значения — числа с плав. точкой | `assert all(isinstance(v, float) for v in res.values())` |
| сортировка по убыванию | `assert list(res.values()) == sorted(res.values(), reverse=True)` |
| сортировка по возрастанию | `assert list(res.keys()) == sorted(res.keys())` |
| округлено до 2 | `assert all(round(v, 2) == v for v in res.values())` |
| топ не больше n | `assert len(res) <= n` |
| вручную посчитанное число | `assert average([1, 2, 3]) == 2.0` |

## Порядок мыслей при написании теста (рецепт)
1. Читаю сигнатуру метода и что он должен вернуть (в code-samples).
2. Запускаю его на реальном файле — понимаю, что возвращает на самом деле.
3. Пишу `assert isinstance(res, dict)` (тип).
4. Пишу проверку типов ключей и значений (`all(... for ...)`).
5. Пишу проверку сортировки (`list(...) == sorted(...)`).
6. Для метрик — проверку округления; для топов — ограничение размера.
7. Для утилит добавляю пример с вручную известным ответом.
8. Запускаю pytest, смотрю, что всё зелёное.
